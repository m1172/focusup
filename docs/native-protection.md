# Native protection implementation

`modules/focusup-protection` is a local Expo module discovered through Expo autolinking. `plugins/withFocusUpProtection.js` configures the iOS host and generates extension targets during prebuild; no generated `ios/` or `android/` files are the source of truth. The module requires a new development/production build. Expo Go and existing binaries use the honest unsupported fallback.

## Shared policy

`src/services/protection/engine.ts` creates a versioned policy from Pro entitlement, native selections, routines, Sleep Mode, Strict Mode and one temporary-access window. The policy includes timestamps and local weekly schedules, not decrementing counters. Active Strict Mode sessions and strict routines win over temporary access. Allowed groups only exclude apps from their own routine; a separate baseline/Strict rule can still protect them. iOS additionally has an explicit system-selected essential-app exception list.

The foreground app reconciles on hydration, entitlement/preference changes, foreground resume and a coarse 15-second interval. Native implementations persist the policy and decide timed protection independently while JavaScript is suspended. Native permission revocation is rechecked. A changed local UTC offset changes the plan signature, so monitor boundaries are reconciled after timezone/DST changes when FocusUp next runs. iOS status checks also reapply the current timestamp policy to remove expired shields. Native apply failures do not become a successful temporary-access window; the prior JS/native plan is retained or restored.

## iOS

The module requests FamilyControls individual authorization only after the user accepts FocusUp's disclosure. Each labelled selection uses Apple's `FamilyActivityPicker`, supporting opaque app/category/web-domain tokens. Users must choose the correct app/group for each label; the app never tries to infer an Instagram identity from an opaque token.

The App Group is `group.<bundleIdentifier>.protection`. The host and three Screen Time extensions use Family Controls entitlements. `FocusUpMonitor` runs DeviceActivity interval callbacks and reapplies the union of active groups through the named ManagedSettings store. `FocusUpShield` provides purple FocusUp copy and visuals. On iOS 26.5 and newer, its primary action uses Apple's public `ShieldActionResponse.openParentalControlsApp` to open FocusUp. The extension records only a labelled destination and timestamp in the App Group; the host consumes the request once and shows `/native-app/instagram` or `/native-app/youtube`. The existing opaque app/category/domain selection identifies the destination; unmatched selections open Protection settings. Requests expire after five minutes, and Apple tokens never enter JavaScript. Older iOS versions close the original app and instruct the user to open FocusUp manually. The shield remains applied throughout the handoff. The optional `FocusUpLiveActivity` widget uses ActivityKit timestamps and exposes a deep link back to FocusUp from supported widget interactions.

Routines repeat with local clock components; weekday checks happen in the shared policy evaluator. The implementation registers at most 16 routine/Sleep monitors plus the timed Strict/temporary monitors. Native iOS timed windows require at least 15 minutes; UI presets are 15/30 minutes for Temporary Access. If native monitoring fails, source state does not claim native enforcement succeeded. OS scheduling delays and system limits require device testing.

Before building for devices/distribution, request Apple's Family Controls distribution entitlement as required for the host and all Screen Time extensions, register the App Group, and provision every extension bundle ID. EAS extension declarations are generated by the plugin. Do not substitute ordinary bundle strings for opaque application/category tokens.

## Android

The library manifest declares one AccessibilityService and an original shield Activity. It does not alter the main app Activity's purchase-related launch mode. The service requests only `TYPE_WINDOW_STATE_CHANGED`, has `canRetrieveWindowContent=false` and `canPerformGestures=false`, and reads only `event.packageName`. There are no root-node, message, text, password, screenshot, or screen-upload APIs.

Only eight explicit social app packages are queried for installation; FocusUp does not enumerate the entire phone. While enabled by the user, the service checks the persisted local policy on window changes and a two-second main-thread loop. Temporary access survives JS suspension/restart through its stored expiry; a foreground app is shielded again when the native service next observes expiry. Android can delay execution under OEM battery restrictions, and no service may claim enforcement after the user disables it.

When a protected original Instagram or YouTube app is opened, the shield Activity opens the corresponding `/native-app/<platform>` handoff page in FocusUp. The persisted policy continues to block the original app. If that handoff fails or another platform is protected, the native shield retains explicit actions to open FocusUp's controls or return to the launcher. Settings and FocusUp itself are never blocked by this package allowlist. The feature is whole-app protection; it does not scan arbitrary Accessibility nodes to guess native Reels/Shorts screens. Google Play accessibility declarations, disclosure review and physical-device checks are external release requirements.

## Browser and original-app entry points

`/browser/instagram` and `/browser/youtube` open the websites immediately. The purple launch page is reserved for `/native-app/<platform>`, the original-app interception/handoff route. Its Open button and link sheet replace that page with the cleaner browser. They never start Temporary Access, remove the native app from protection, or launch the original social app. Instagram's app settings include an entry to configure native app protection; enabling it requires the existing Pro access, a native device build, system authorization, and an explicit app selection. Simulator inspection can verify these routes, but cannot verify Screen Time authorization or interception of a real app. Apple's supported action is documented at https://developer.apple.com/documentation/managedsettings/shieldactionresponse/openparentalcontrolsapp.

## Clearing data

Native reset removes only the named FocusUp ManagedSettings store, app-group selections/plan, own ActivityKit activities, or Android module preferences. Browser clearing uses the app's WKWebsiteDataStore and app cookie/cache stores on iOS; CookieManager/WebStorage/WebView app stores on Android. It does not touch Safari/Chrome or unrelated phone data. The JS clear service removes only `focusup-` and `@focusup/` AsyncStorage namespaces and own reminders. RevenueCat's store identity is retained. No cookies or tokens cross into JS.

## Validation in this continuation

TypeScript and Jest validate policy and local app logic. Expo autolinking resolves the module for both platforms. The extension plugin was exercised twice against an in-memory copy of the existing Xcode project and wrote only scratch outputs, confirming four extension targets without duplicate targets. Swift source passed parser checks. No Xcode/Gradle compilation, app build, permission prompt, native shield, Live Activity, or device timer was executed. These checks do not validate native binary behavior.

The local iOS module and generated extensions include privacy manifests for their own App Group defaults usage. This does not replace the app-level store/privacy disclosure for RevenueCat or the social providers. English, Russian and Uzbek camera, microphone and photo-library usage descriptions support user-initiated provider uploads; WebView media capture stays in prompt mode and no permission is requested at launch.
